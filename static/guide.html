1Before race day

  1. Create the event
    Pick a short code like siliguri10k. It appears in every public link, so keep it easy to type.
  2. Add a race for each distance
    A 5K and a 10K on the same morning are two races in one event. Each is ranked on its own, so nobody is placed against a field that ran a different distance. Even a single-distance event needs one.
  3. Add checkpoints to each race
    Every race needs exactly one marked finish. Splits are optional but make the results far more interesting.
    Watch out: checkpoint names are unique across the whole event, not per race — volunteers pick from one flat list. Name them 5K Finish and 10K Finish, never both "Finish".
  4. Load the start list
    Paste bib, name, category, gender one per line, or upload a CSV that may also carry a race column so one file covers every distance. Re-importing is safe — bibs already entered are skipped.
    Check the per-race counts shown next to each race afterwards. A whole distance imported against the wrong race is obvious there and painful to spot later.
  5. Upload artwork and print the bibs
    A 3:2 image around 3000 × 2000 px works best, with the focal point centred and no text in the image. Two bibs fit an A4 sheet.
    Print one first and look at it on your actual printer before committing to a few hundred. Full-bleed artwork looks best but uses a lot of ink; the band layout is cheaper and reads better at distance.

3On the morning

  1. Set up each volunteer phone while you still have wifi
    Open /checkpoint.html, enter the event code, pick that phone's checkpoint, and wait for the clock sync to finish. It caches the start list, so from then on it works with no signal.
    Why the clock sync matters: a phone that is eight seconds fast silently adds eight seconds to every split it records, and nothing downstream could detect it. Each device measures itself against the server and corrects every scan.
  2. Add it to the home screen, leave the screen on
    A locked phone stops scanning.
  3. Fire the gun as the race starts
    From Race admin. For a staggered start, set each race's own start time instead of the event gun.
    Never fire the gun afterwards. Scans that predate the start time produce negative elapsed times, which show as 0:00:00 rather than raising an error.
  4. Scan bibs as runners pass
    The whole screen flashes the bib number so a volunteer can confirm it at arm's length in sunlight. Repeat scans of the same bib within eight seconds collapse into one sighting. A bib can always be typed by hand.

4During and after the race

  1. Anyone follows the live leaderboard
    Share /results.html#your-event-code. Search by name or bib, filter by race, status or category, and tap a runner for their splits and placings. It refreshes itself every ten seconds.
  2. Check the raw reads before publishing
    Race admin lists every sighting the system has received. Look for clock-drift warnings, unknown bibs, and anyone showing a late split but no finish. A suspect read can be voided — excluded from timing while the row itself is kept.
    Nothing is ever deleted. That is what lets you correct a mistake and re-derive the results instead of arguing about them.
  3. Runners print their certificate
    At /certificate.html they pick the race and find themselves by name — most people have binned the bib by then. It carries their finish time, overall and category placings, splits and average pace, on the race artwork.

◆Three things that keep it honest

Clock correction

Every scan is corrected by that phone's measured clock offset. The raw device time and the correction applied are both stored, so a disputed result can be audited afterwards.

Idempotent ingest

Each scan gets a unique id generated on the phone, and that id is the primary key. A phone coming back from a dead zone can resend its whole queue as often as it likes without creating duplicates.

Append-only history

Every sighting is kept exactly as it arrived. Results are recomputed from them on demand, so voiding a bad read fixes the leaderboard on the next refresh with no migration and no repair job.
